# A: Inventura jádra pro OPSYS

Stav: analýza kopie jádra (git commit `b709d86`, 2026-10-14), nic se nespouštělo ani neměnilo. Cesty jsou od kořene
`systemy/interni-system-opdigital/`. Co jsem v kódu nenašel, je označeno „nenalezeno“. Čísla řádků jsou orientační (stav kopie).
Pozn.: specifikace v `docs/specifikace/` říká „OPSIS“, zadání „OPSYS“; viditelný název systému je jen v `clients/<slug>/config.ts` (`branding.name`).

Jádro v kostce: pnpm monorepo, Next.js 16 (jedna generická trasa `app/(app)/[...path]/page.tsx` pro seznam a detail všech entit),
Drizzle + PostgreSQL, pg-boss, Better Auth. Moduly (9): `kontakty, zakazky, poptavky(=CRM), realizace, fakturace, dochazka, sklad, stroje, kalendar`.
Moduly se **zapínají jen v `clients/<slug>/config.ts`** (`modules`); vypnutý modul nezanechá stopu a jeho tabulky se nevytvoří (migrace jen pro zapnuté).
Žádné `if (slug === …)` v jádru (hlídá `tests/guards.test.ts`; stejný test zakazuje v kódu slovo „rebar“ mimo `@rebar/*`).

## 1. Anatomie modulu krok za krokem

Vzor: `packages/modules/stroje` (nejúplnější životní cyklus: manifest, schéma, entity, příkazy, upozornění, metriky nástěnek, widgety,
kalendářní vrstvy, úlohy, terminál, UI). Menší vzory: `kontakty` (jen data+entity), `kalendar` (příkazy, úlohy, ics).
Velký modul se dělí na „oblasti“ (`poptavky/src/crm/<oblast>/`): každá oblast exportuje `defineModuleServer` + `areaUi`, modul je skládá přes
`mergeServers(...)` (`packages/core/src/modules/server.ts`) a `mergeModuleUi(...)` (`poptavky/src/crm/merge-ui.ts`). Dobrý vzor pro rozdělení práce.

### 1.1 Zapnutí modulu v `clients/<klient>/config.ts`

```ts
const MODULES = ["kontakty", "obchody", /* …nové moduly… */] as const;
export default defineClientConfig({
  slug: "opsys", branding: { name: "OPSYS", shortName: "OPSYS", accentColor: "#2563eb" },
  modules: [...MODULES],                       // závislosti (dependsOn) se kontrolují při startu
  dashboards: { enabled: true, defaults: standardDashboards(MODULES) },   // nebo vlastní seedDashboard(...)
  terminal: { roles: [], tiles: [] },          // OPSYS nepoužívá; výchozí dlaždice mají klíče dochazka/zakazky (jen se nezobrazí)
  notifications: { events: { "<klíč>": { recipients: [...] } } },
  security: { require2faRoles: ["owner", "partner"] },
});
```
Nový klient: `pnpm client:new opsys --name "OPSYS"` (zkopíruje `clients/_template`; balíček `@client/opsys`; pak `pnpm install`).
Sestavení vybírá klienta proměnnou `CLIENT` (`apps/web/next.config.ts`: aliasy `@client/config`, `@client/extensions`); kontrola bez běhu: `pnpm config:check`.
Nastavení → Moduly je jen přehled, přepínač za běhu **neexistuje** (změna = nové sestavení).

### 1.2 Checklist „nový modul za 14 kroků“ (po předpřípravě z §2 zbývají kroky 3–13)

1. `packages/modules/<id>/{package.json,tsconfig.json,drizzle.config.ts}` (kopie `stroje`, přejmenovat; `pnpm install`).
2. `src/index.ts`: manifest (id, name, icon, `nav`, `permissions`, `entities`, případně `notifications`, `seed`).
3. `src/schema.ts` (konvence ADR 002/003) → `pnpm --filter @rebar/<id> db:generate`.
4. `src/entities.ts` (`defineEntity` s `listPath`, atributy, `search`, oprávnění).
5. `src/commands.ts` (`<id>.<akce>`, Zod vstup, handler v `inTx`, audit, `notify`).
6. `src/server.ts`: `defineModuleServer({ entities, commands, dashboardMetrics, widgets, attention, jobs, … })`; exportovat `server`.
7. `src/ui.tsx` (volitelně): `defineModuleUi({ recordTabs, recordActions, pages, … })`; exportovat `ui`.
8. Zapojení (8 souborů, tabulka §2 skupina A): `ids.ts`, `modules.ts`, `modules-server.ts` (`SERVERS`), `modules-ui.ts`, `apps/web/package.json`, `next.config.ts` (`transpilePackages`), `eslint.config.mjs` (`MODULES`), `tests/package.json`.
9. Oprávnění do rolí: seed klienta (`RoleDef`) + ikony do `ICONS`, je-li nová.
10. `config.modules` klienta (+ případně `dashboards.defaults`).
11. Testy: unit + `*.int.test.ts` (oprávnění po rolích, souběh) + `PROBES` pro každý příkaz.
12. `pnpm docs:scaffold` → doplnit `docs/moduly/<id>.md`; řádek do `docs/NOTIFICATIONS.md` (jsou-li události); `CHANGELOG.md` (Unreleased).
13. `pnpm db:migrate && pnpm db:seed` (lokálně `pnpm db:up`), `pnpm dev`.
14. `pnpm docs:refresh` + `pnpm check` (formát, lint, typy, docs, testy, `config:check`).

## 3. Co jádro umí vs. požadavky OPSYS

Legenda: UMÍ / ČÁSTEČNĚ / NEUMÍ. „Nenalezeno“ = hledáno v `packages/`, `apps/`, `scripts/`, `docs/`.

| Bod | Stav | Kde to je / co chybí |
|---|---|---|
| **(a) Viditelnost shared/private, zámek** | **NEUMÍ** | Žádný sloupec `visibility`/`private` (nenalezeno). Existuje jen rozsah oprávnění `all`\|`own` (`rbac/types.ts`, `rbac/permissions.ts`, `entities/engine.ts:119 scopeWhere`, `EntityDef.ownerColumns/scope/owners` v `entities/types.ts`); `own` se vyhodnocuje **jen když role nemá `all`**, takže owner (`all`) vidí vše a záznamová viditelnost se nedá vyjádřit. Ikona `lock` v `ICONS` je. Místa, která musí vynutit „soukromé“ (každé jinak uteče): `entities/engine.ts` (`scopeWhere` → `whereOf` → `queryRecords/queryGroups`, `ownersOf` → `getRecord/updateRecord/deleteRecord`), `entities/policy.ts#assertEntityAccess` (komentáře, úkoly, soubory, časová osa, notify), `entities/search.ts#searchAll` (obě větve `all` i `own`), `entities/aggregate.ts` + `dashboards/metric-helpers.ts` (součty přes `buildEntityWhere`), `export/entity-export.ts`, `collab/tasks.ts` (`listMyTasks`), `notifications/notify.ts` (příjemce musí záznam smět číst), `audit_log` (nemá sloupec viditelnosti). **Mimo centrální vrstvu**: `attention`, `widgets`, `calendarLayers`, `dashboardMetrics`, `costProviders` modulů čtou přes `ctx.db` samy → každý musí použít společný predikát; žádné RLS v PostgreSQL (`rebar_app` je jedna role). Nutné: nový společný hook v `EntityDef` (např. `visibility`), predikát v `whereOf/searchAll/policy`, dědičnost na děti (`visibility_source`), test na každou cestu čtení (viz `docs/specifikace/11-architektura-tech-stack.md` §Engine oprávnění) |

## 4. Nejrizikovější místa pro přestavbu

Důležité zjištění předem: **modul nemusíš z repa mazat, stačí ho nezapnout** v `clients/opsys/config.ts` (tabulky se nevytvoří, UI, oprávnění ani navigace se nesloží). Jenže `MODULE_IDS`/`ALL_MODULES` a testy dál obsahují všech 9 modulů, takže `pnpm check` je zkouší sestavit. Skutečné **smazání** balíčků naráží na tvrdé vazby níže.

1. **CRM (`poptavky`) je navázané na zakázky, ne samostatné.** `dependsOn: ["kontakty","zakazky"]`; obchod = řádek `job` s 13 sloupci `crm_*` ve schématu zakázek (`zakazky/src/schema.ts:88-108`), `phaseHooks` s `entity: "job"` (`poptavky/src/crm/hooks.ts`), 25× import `@rebar/zakazky/schema`, 12× `@rebar/zakazky/server`, 4× `@rebar/zakazky/phases` (`PHASE_LIST`); FK `crm_follower.job_id → job` (`poptavky/drizzle/0001_crm_aktivity.sql`). Odstranění `zakazky` = přepis CRM. Doporučení: nový modul s vlastní entitou `deal` a kopií chování, `poptavky` jen nezapínat.
2. **`apps/web` importuje moduly staticky**, takže smazání balíčku rozbije build, i když je modul vypnutý: `server/modules-server.ts:21` (`PHASE_LIST` ze `@rebar/zakazky/phases` v `buildRegistry`, guard je jen runtime), `app/(app)/home-clock.tsx` (`@rebar/dochazka/ui`), `app/api/fakturace/**` (4 trasy), `app/api/zakazky/[id]/nabidka/pdf`, `app/api/investor/**`, `app/investor/**`, `server/investor.ts`, `app/tisk/denik`, `app/tv`, `app/api/kalendar/feed/[token]/route.ts` (kalendář importuje `crmApi` z `poptavky` na úrovni aplikace, balíčky na sobě formálně nezávisí). Dále natvrdo `app/(app)/page.tsx` (zakázky, deník, docházka, `/zakazky/...` odkazy) a `mobile-nav.tsx`.
3. **Měkká vazba přes klíč entity `"job"`**: `stroje`, `sklad`, `dochazka`, `kalendar` volají `assertEntityAccess(c, "job", …)`, `visibleRecordTitles(…, "job", …)` a mají atributy `record: { entityType: "job" }` (stroje `commands.ts` 8×, sklad 3×, kalendar `entities.ts:88`, dochazka `server.ts:115`). Bez entity `job` v registru `assertEntityAccess` vyhodí „Tento typ záznamu není v systému povolen“ (`entities/policy.ts`), jen `dochazka/metrics.ts` používá bezpečné `tryScopedEntity`. `realizace` a `fakturace` mají tvrdou závislost (`package.json`, `dependsOn`).
4. **Jádro zná pojmy starých modulů**: `extensions/types.ts` (`EventMap`), `terminal/config.ts` (výchozí dlaždice `dochazka.clock`, `zakazky.today`…), `seed/default-roles.ts` (role owner/office/foreman/worker s `zakazky.*`, `fakturace.*`, `dochazka.*`), `notifications/money.ts` (`MONEY_PERMISSIONS = zakazky.economics, fakturace.read`), `dashboards/defaults.ts` (sady nástěnek s `needs`), `dashboards/evaluate.ts` (`autoAttr(.., "job")`: filtr „Zakázka“ nástěnek hledá atribut typu `record` → `job`), `entities/phase-hooks.ts` + `config-data` (`setPipelinePhases("job")`). Většinou jen výchozí hodnoty/guardy, ale změna je v jádru, kde pracuje „jádrový“ agent.
5. **Kontakty** (`kontakty`) drží vše nahoře (závisí na nich zakázky, fakturace, sklad, poptávky); zůstat. Slučování firem/osob se řídí introspekcí DB (`merge.ts`), takže nové sloupce `company_id`/`person_id` a polymorfní `entity_type/id` se zahrnou samy (ověřit u modulů, které je pojmenují jinak). `kontakty/src/commands.ts:34` má v oprávnění klíče `poptavky.write`, `zakazky.write` (bez těch modulů jen neplatí).
6. **Testy, které předpokládají celou sestavu**: `tests/support/security-fixture.ts` (`buildFixture` zakládá zakázky, faktury, sklad, stroje, docházku; používá ho `security-matrix`, `public-surface`, `query-count`), `tests/demo-seed.int.test.ts` + `clients/demo/seed/*` (stories A–D), `tests/package.json` (závislosti na všech balíčcích), e2e `apps/web/e2e/*` a `e2e-crawl/*` (klient `demo`), `docs/reference/**` a `tests/docs.test.ts` (dokument pro každý `MODULE_IDS`). Odstranění modulu = úprava všech těchto míst.
7. **Konvence, které agenty zdržují**: jádro hlídá slova z klientů a „rebar“ (`tests/guards.test.ts`), každý veřejný route handler potřebuje záznam v `PUBLIC` a limit (`security-static.test.ts`), nový export bez JSDoc shodí lint, nový příkaz bez probe shodí `security-matrix`, nová událost upozornění bez řádku v `docs/NOTIFICATIONS.md` shodí `notifications-docs.test.ts`, `pnpm check` obsahuje `docs:check` (po každé změně kódu je nutné `docs:generate`).
8. **Migrace**: pouze dopředné (ADR 009); jakmile v DB tabulky vzniknou, změna schématu „contract“ krokem. Jádrové migrace (0012+) a jejich snapshoty se musí tvořit sériově. Audit/viditelnost/koš/štítky (§3 a, c, d, e) je změna **sdílených tabulek a engine**, rizikovější než jakýkoli jednotlivý modul, a proto první v pořadí.
